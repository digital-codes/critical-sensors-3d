# Design

## Context

`orchard/src` is eleven TypeScript modules (~2,200 lines) loaded by a Vite
app. Configuration currently lives inline in the modules that use it; the
inventory below is what moves. `site.json` (generated by
`orchard/tools/prepare_site.py`) is the established data home for
site-anchored values and already works that way for `cameraPresets`,
structure footprints and window bounds.

Inventory of verbatim configuration (grep-verified 2026-11-07):

- `flight.ts` — `WAYPOINTS` (6 site-anchored [x, clearance, z] tuples),
  `DURATION_S`, `BOB_AMP_M`, `BOB_HZ`, `SWAY_AMP_M`, `SWAY_HZ`,
  `LOOK_AHEAD_M`, `LOOK_DIP_M`, `YAW_TAU_S`
- `main.ts` — solar parameters (site latitude 48.9899, declination
  constants 23.44/284/365, sun anchor `[10, 117, 0]`, orbit radius 400,
  intensity curve 0.3 + 0.5·sin(alt)), shadow frustum (mapSize 2048,
  extent ±90, near 50, far 600, bias −0.0005), ambient light
  (0xffffff, 0.25), month names + month lengths (day-of-year mapping),
  `__buildId` debug string
- `sky.ts` — `CLOUD_COUNT`, `CLOUD_SPAN`, `GROUND_Y` (115; main.ts's sun
  anchor implies 117 — the two must not silently diverge once collected)
- `grass.ts` — blade `COUNT` (90000), `BLADE_W`, `SNOW_TINT`, blade height
  range (0.22 + rand·0.55), further tuning further down in the file
- `seasons.ts` — the `SEASONS` table (day anchors, leaf factors, tints)
- `structures.ts` — material colours (wood 0x4a3728, cream 0xd8cfae, snow
  0xe8edf2, tarp 0x3f6f96) and construction dimensions (post radii, deck
  height, slat spacings, rail height, roof/fabric tilts)
- `camera.ts` — damping factor 0.08, polar-angle margin 0.02, distance
  limits (verify exact names during apply)

## Goals / Non-Goals

**Goals:**

- One typed module `orchard/src/config.ts` is the single home for every
  app-level tunable; modules import, never re-declare.
- Zero behaviour change: identical rendering, identical camera/flight
  behaviour, identical `window.__rig`/`__scene3`/`__buildId` hooks
  (`__buildId` keeps its exact string, only its home moves).
- Grep-verifiable acceptance: after the change, the only numeric literals
  left in the moved modules are algorithm-internal values with comments
  (loop steps inside mesh-construction helpers stay local — they are
  geometry detail, not settings, and the spec-tasks say so explicitly so
  the sweep has a defensible boundary).

**Non-Goals:**

- No values move into code that belong to generated geodata: `site.json`
  keeps camera presets, footprints, window bounds; `prepare_site.py` is
  not touched.
- No behaviour tuning "while we're in there" — the 115/117 ground-level
  discrepancy is *collected* (one place, both uses point at it) but NOT
  resolved to a single value in this change.
- No hot-reload/settings-UI mechanism — `config.ts` is still compiled in.

## Decisions

- **`config.ts` module, not JSON.** The values are consumed by typed TS
  modules; a JSON file would need a loader, runtime typing and async init
  for zero benefit — none of these values change without a rebuild anyway
  (they are not per-deployment data like site.json, which stays generated).
  Alternative rejected: extending `site.json` with a `config` section —
  that file is overwritten by `prepare_site.py`, so hand-tuned app values
  there would be clobbered on the next site regeneration.
- **Sectioned single file, not per-module config files.** One
  `config.ts` with clearly delimited sections (SUN, CAMERA, FLIGHT, SKY,
  GRASS, SEASONS, STRUCTURES, DEBUG) satisfies "collect constants in a
  single place" literally and keeps review trivial; per-module files
  would just move the scattering.
- **`seasons.ts` keeps its module + type, imports the table.** The
  `SeasonDef` type and interpolation logic stay; only the data moves.
  Same pattern for everything else: logic stays, data moves.
- **Export shape:** `export const CONFIG = { ... } as const;` plus named
  re-exports where a module wants a bare identifier — keeps tree-shaking
  and makes grep for `CONFIG.` the verification hook.

## Risks / Trade-offs

- A transcription typo silently changes behaviour → mitigated by the
  pixel-probe verification task (screenshot before/after at fixed camera
  preset + fixed day-of-year, compare) and `npm run build` type-checking.
- config.ts becomes a dumping ground over time → the file gets a header
  comment stating the admission rule (site-anchored/generated → site.json
  via prepare_site.py; app tunable → config.ts; algorithm-internal →
  local constant with comment).
- Shadow-frustum or solar literals mis-transcribed would only show at
  certain days-of-year → the probe task renders a summer and a winter
  day, not just one.

## Addendum (during apply, user-directed)

- **Fixed-seed option.** Plain pixel comparison is confounded: grass and
  clouds are seeded by `Math.random()` per page load (measured load-to-load
  noise floor ≫ any plausible refactor delta). Resolution per the user:
  `?seed=<n>` URL param → mulberry32 (`src/rng.ts`) wired through grass +
  sky (the only random consumers — trees carry per-tree seeds from
  site.json). Unseeded behaviour unchanged. This turned verification into
  an exact seeded A/B against the pre-refactor tree (worktree at faca603
  with identical wiring): summer mean|diff| 0.012/255 (0.085 % of pixels
  >8, antialiasing jitter), winter 5 px — pixel-identical.
